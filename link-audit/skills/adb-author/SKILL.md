# 製作 .adb：通用建立、驗收與交付流程

本 skill 只講**通則**。特定文字的差異（原料在哪、跨庫目標是誰、代號與命名、專案特有缺口）
請放在該文字的覆蓋 skill（例如 `ybh-adb-package`），**不要在這裡重複**。

## 為什麼驗收必須用閱讀器自己的程式

這是整條流水線最重要的一點，也是我們付過學費的地方。

「打包成功」不等於「開啟是對的」。若自己寫一套檢查，就會出現**驗收全綠、畫面卻是錯的**：
我們真實發生過兩次——
- 用命令列的 `toc` 驗目錄樹，連三輪都報「巢狀正確」；而介面實際走的是另一條建樹碼路
  （只認父節點自己的 `t=` 宣告），使用者一開介面看到的是全部平舖的根節點。
- 發射端與統計端各寫一份「表格行取什麼內容」的規則，同一條記錄兩邊判定不同，於是發射數字不可信。

**結論：驗收的標準必須是閱讀器實際執行那支程式**（`renderEmbed`、`parseTableBlock`、
`buildTree`、`nodeAnchorInfo`、`anchorVa`、`pageHanTextOf`……），不是重建它邏輯的平行實作。
因此本地打包在原理上需要 accelon26 的 TypeScript 原始碼與被參照的目標庫底座（如大正藏）。
這不是設限，是為了避免上面那種「綠給你看」的失敗。

## 步驟 0：環境體檢（先跑這個，不要直接建置）

一定要有一個能一次報告「缺什麼」的入口。最小要求：

- 檢查：原料目錄、中繼目錄、成品部署目錄、跨庫目標底座（.adb）、打包器模組、reader 模組、
  表格／錨點解析模組。
- 區分**必備**與**可選**，缺必備時明確失敗並列出名字。
- 提供 `--json` 輸出，方便對方貼回來回報環境。
- **不含任何憑證與個資**。

路徑一律走一處集中定義、可用環境變數覆寫（預設＝維護者的佈局）。
**不要**把絕對路徑寫死在各支指令碼裡：換機器的人只會看到跑到一半才 `Cannot find module`，
既不知是環境問題還是指令碼壞了。

## 步驟 1：原料結構化

把 Markdown 的隱含結構變成標籤。**只在原料沒有線索時才建立假結構**——這是紅線。

原則：
1. **標題定義才算定義**。文內引用同一個 id 不計入「此 id 存在」。計數規則寫錯會把問題放大
   （我們曾因寬鬆比對，把「跨卷撞號」從千分之幾報成十萬條）。
2. **兩套制式不同就不要硬對**。若源頭用階層式編號（換父即復位）而平臺用流水號，直接互查的低成功率
   是制式差異，不是 bug；要匹配就按縮排重算父內序＋標題字首＋行距最近，並把不合格的**如實標為平列**，
   絕不虛構父子層級。
3. **缺字／異體字優先取既有 Unicode 碼位**，先查前後文是否已有可用字，再考慮造字。
   判定「是不是漢字」要用產品那套（`\p{Script=Han}` 帶 `u` flag），不要用 `[一-鿿]`——
   後者會漏掉擴充 A 區的字，產生假的「找不到」與錯位窗。
4. **正文內容的取捨不屬於轉檔端**：改寫、刪節、補文、錯字修正，都要資料維護者裁示。

## 步驟 2：互鏈分層

各種鏈結各司一件事，混用就會同時出現「點了沒反應」與「不知道點的是哪個」：

| 目的 | 標記 | 注意 |
|---|---|---|
| 跳到另一庫的精確位置 | `<聯 i="db?頁欄#起-迄">` | 座標要含足以定位的層級（若頁碼跨冊重複，**一定要帶冊號**） |
| 不離卷的行內速覽 | `<嵌 i="db?頁欄" j="起-迄">` | `j` 的座標系必須與渲染器一致（漢字偏移 vs 含標點偏移，兩者混用必錯位） |
| 庫內節點定位 | `<節聯 n="卷#錨">` | 錨點要能解析到 VA，且篇級／卷級語義要有負控 |
| 把同一份本文就地填入各套大綱 | `<融 i="…"></融>` | **必須成對且內容留空**；自閉合會讓渲染器吐未閉 span。`max` 的單位是「行」不是字元，要實測定檔，不要憑感覺放大 |

**座標系換算是這裡最容易錯的一處**：搜尋引擎回的 VA 走「含標點的字元」位置，而頁內取段函式回的是
「只剩漢字」的字串。兩者相差可達每頁一二成，直接把 VA 偏移拿去漢字串 `indexOf` 會永遠找不到，
看起來像「這句話不存在」——其實是沒換算。跨頁／跨欄同理：句子起點落在欄尾時要**鉗到頁尾發半句**
並記錄，而不是放棄或改指別欄。

## 步驟 3：窗（行內座標）的產生與閘門

1. 定位用**引擎檢索**（連寫階梯：先長串，不中就縮短），不要把目標庫全文抽進管線。
2. 命中後 greedy 延伸到最長一致片段，再換算成渲染器用的座標系。
3. **最後一道閘門是產品自己的渲染器**：逐條呼叫 `renderEmbed`，要求回傳的高亮片段漢字數
   **恰好等於** `迄−起`，且窗首若干字與引文相符。不符合者**就地剝窗**（降級為較粗但正確的形態）。
   寧可少給，不發一個「點開是別句話」的窗。
4. 統計可補數量時，**先建正控再量尺**：拿一已經過驗證的既有批次當標尺量，量不到的比例就是尺的天花板；
   不先建正控會把「尺搜不到」誤報成「資料沒有」。
5. 需人工判定的（短串唯一性可疑、多處命中、靠較寬鬆方法救回的）要拆成**逐條清單**交付，
   不要混進自動發射的基數。

## 步驟 4：驗收（每一類都要有明確判準與負控）

通用檢查類別（特定文字把對應指令碼列在覆蓋 skill 裡）：

| 類別 | 驗什麼 | 判準 |
|---|---|---|
| 本體 | 大小、sha256、區塊數 | 記下來供交付比對 |
| 庫內錨點 | 每個目標能解析到 VA | FAIL 必須 0；**要有負控**（不存在的錨必須失敗、篇級與卷級首筆不得相同） |
| 跨庫座標 | 每種座標能在目標庫解析 | FAIL 必須 0；地址鍵含冊號、零填充要先轉數字再比 |
| 行內窗 | 從**已部署位元組**回讀並用 `renderEmbed` 比窗首 | 高亮漢字數等於 `迄−起` |
| 目錄樹 | 走介面實際那條碼路（不是 CLI） | 根數／節點數等於期望；跨樹鏈汙染要有專項檢查 |
| 特殊區塊 | 成對性、自閉合計數、抽樣填入 | 未閉合必須 0 |
| 標籤／結構 | 表格段、清單段被產品解析器接受 | 不接受的維持純文字並記錄原因 |

**三條紀律**：
- **同一判定只允許一份實作**：能組合既有腳本就不另寫，避免兩套標準各自漂移。
- **驗收的檔案必須等於交付的檔案**：有並行重建時，先比 sha 再下 PASS。我們真發生過
  PASS 記在重建前的位元組上、而部署的是另一顆。
- **驗收腳本自己也必須在版控裡被執行**：委派子腳本要用**絕對路徑**，不要用 `cwd` ＋相對檔名——
  後者會解析到中繼目錄裡的同名副本，於是「PASS 記的是未入版控的那份程式」，而你 review 過的那份
  根本沒跑。我們就這樣發現中繼目錄躺著 46 支同名副本，其中一支在**邏輯上領先**版控
  （多承認一種已驗證窗的標記）；只把 cwd 改對而不回合該內容，會讓驗收變嚴而誤報。
  定期攤開這種分岔時：先正規化掉「路徑改造」類差異（否則假陽性淹沒真問題），再給出
  「誰較新」的方向線索；但 mtime 只是線索，不等於內容較新。

## 步驟 5：交付與部署

1. 先備份舊版（備份目錄要 gitignore；大檔不入版控）。
2. **檢查部署目標是不是硬鏈**（Windows：`fsutil hardlink list <路徑>`）。若是，就地截斷寫入會
   **連帶改掉其他名字指向的檔案**（可能是別人的測試底座）。正確做法：先把這個名字移走，
   再放入新檔成獨立 inode，並前後比對各路徑 sha。
3. 交付後**對部署那顆重新驗一次**。
4. 查證成品內容一律走引擎解碼路或 MCP API：**對 .adb 做位元組 grep 無效**——正文標籤以 id 編碼，
   `grep '<標記'` 得 0 筆不代表資料不存在。
5. 行號是**行表**，不是文字裡的 `\n`：把區塊串接後 `split('\n')` 會得到「1 行」的錯答案；
   要用 `lineText(i)` 或行級 API。

## 步驟 6：記帳與版控

- 專案的結論正典（一份摘要檔）新增一節：版號、改了什麼、各節實測數字、成品 sha 與大小；
  並在同檔的**勘誤表**如實記錄自己這輪犯的錯——這是讓下一個讀的人不重踩的唯一有效機制。
- commit **只加明確路徑**，**不要用 `git add -A`**：備份目錄、卡片暫存、執行期狀態、客戶資料
  常在未受控清單裡，一次 `-A` 就可能把不該進公開歷史的東西送進去。
- 提交前先看 `git status`：工作樹若有不是自己做的未提交改動，先辨明歸屬，不要打包進自己的 commit。

## 邊界

可以獨立完成：原料結構化規則、發射標記、探針與清單、重建、本地驗收、本地部署、本倉提交與推送。

必須停下交人（寫成自包含單據，帶檔名＋行號＋重設資料＋修復後可對的數字）：
1. **需要閱讀器（accelon26）配合**的問題——不動它的 `ts/src/`、`wails/`、釋出指令碼、exe、`versions.json`。
2. **發布到官網**——上架、站內清單、授權與公告文字由官網維護者執行。
3. **正文內容取捨**（改寫、刪節、補文、錯字）由資料維護者裁示。
4. 時間承諾、對外公告、影響其他文字庫的動作。

## 已知缺口要這樣記（避免白費工）

寫缺口時要分三種，並各給判定方法：
- **源頭缺**：等源頭補編即癒合，不要硬改成「最近的下一個」（例：某些論的科判源頭未編完）。
- **本質做不到**：結構上無解（例：上級節點只有標題、沒有自己的正文行；義引沒有逐字對應）。
- **待修**：能重現且定位明確者才進清單，並附重現方法與實測數字。
