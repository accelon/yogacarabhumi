# skills/ —— adb 製作技巧庫（將發布到官網分享）

這裡放的是**給維護者與它的 agent 用的可執行知識**（skill＝一份 `SKILL.md`，frontmatter 加內文），
不是文件、不是 log。判準只有一條：**照著做完，東西真的能跑**。

## 一、分層：核心與覆盖

    skills/
      README.md                     ← 本檔：慣例與規則
      adb-author/                   ← 通用核心：原料 md → .adb（打包＋驗收＋交付紀律）
      adb-inspect/                  ← 通用核心：讀任何 .adb（走 adb MCP API，禁位元組 grep）
      ybh-adb-package/              ← 專案覆盖：只寫《瑜伽師地論》與其他文本不同之處
      <text>-adb-package/           ← 日後其他法师各自新增

**規則是「重複的地方只能有一份」**：通用流程（驗收六類、交付前後 sha、硬鏈部署、行號是行表不是
`\n`、提取規則只能一份實作……）一律寫在 `adb-author`；專案覆盖**只允許**寫：原料在哪裡、跨庫目標是誰、
著作清單與代號、專案特有的閘門與缺口、以及本專案工具的路徑。
理由不是整潔癖：我們真發生過同一批資料被兩支腳本各寫一份規則，同一條記錄得到不同判定。
skill 也一樣——两处写同一件事，将来就会有一处是错的。

## 二、一個 skill 必須具備

1. **frontmatter**：`name`（kebab-case、與目錄同名）、`description`（第三人稱，寫清楚**做什麼**與
   **什麼時候用**，這是被找到與被选中的唯一依據）、`version`（semver）。
2. **步驟可直接執行**：命令要能複製貼上；參數、環境變數、預設值都要寫出來，不能假設讀者知道我們的磁碟佈局。
3. **前提與依賴要誠實**：需要哪些外部原始碼或檔案、缺了會怎樣、替代方案及其代價。
   （範例：本地打包需要 adb-converter 的 TypeScript 原始碼，因為驗收用的就是閱讀器那支 `renderEmbed`／
   `parseTableBlock`；不寫這段，讀者會跑一半遇到 `Cannot find module` 而不知道是環境問題還是我們做錯。）
4. **邊界**：什麼可以自己做、什麼必須停下交人。寫成可判定的兩類，不要寫「小心處理」。
5. **已知缺口**：區分「待修」與「本質上做不到」，並說明**不要把它當工數**（例：源頭科判未編完的死錨、
   上級節點沒有正文首行）。這條能擋掉大量白費的工。
6. **驗證手段**：每個宣稱要附「怎麼量的」。沒實據的要寫「未驗證」，不圆話。

## 三、禁止進入 skill 與打包檔的東西

- **任何憑證**：路徑可以寫（`.local/smtp.json` 之類），值一律不得出現、不得印出、不得複製進信或 log。
- **客戶個資**：電子信箱、通訊軟體帳號、IP、瀏覽器 UA、來信全文。官網分享等於公開出版，
  這些一旦進檔就進歷史。
- 大体积成品（`.adb`、`.zip`、備份）——skill 只放方法與指令，不放產物。
- 絕對路徑作為**唯一**可行值：要寫成「可用環境變數覆寫，預設值＝我們的佈局」。

## 四、版本與打包

- **semver**：破壞性變更（步驟改了、參數名稱改了）進 major；新增能力進 minor；文字修訂進 patch。
- 每次打包都要產生**確定性**輸出與可比對的雜湊：同一份來源重複打包，zip 內條目順序與時間戳要一致
  （否則官網的 sha256 每次都在變，維護者無從判斷到底改沒改）。
- 上架清單沿官網既有模式（同 `www/adb/manifest.json`／`www/releases.json` 的形狀）：

      { name, version, description, file, sha256, size, buildTime, requires, notes[] }

- 交付前必跑的檢查：
  1. 解壓後 `SKILL.md` 在 `<name>/SKILL.md` 且 frontmatter 可解析、`name` 欄與目錄一致；
  2. `description` 非空且不含內部代號之外的敏感字；
  3. 掃一遍無憑證／個資樣式（email、IP、`password`、token）；
  4. **照著 skill 從頭執行一次**（至少在乾淨環境跑「步驟 0 體檢」），跑不通的 skill 不发布。

## 五、待使用者決定的兩件事

1. **skill 的正本放哪裡**：現行放在 ybh 工作區（本目錄）。既然要跨文本共用與官網分享，
   正典位置建議移到中性且與發佈工具同處的地方（例如母區 `skills/`，它已有 `mcp/` 之類共用資產），
   各文本倉只留自己的覆盖目錄並引用核心。這一搬動會影響别人，所以沒有擅自動手。
2. **授權與具名**： adb 官網目前對資料庫用 CC0／Apache-2.0 的標注方式；skill 要採哪一種、
   以及「誰寫的」如何呈現（維護者具名？「由 accelon26 維護團隊」？），需使用者定。
   這會寫進 skill 的 frontmatter 或清單頁，事後改比事前定麻煩。
