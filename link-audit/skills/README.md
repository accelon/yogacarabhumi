# skills/ —— adb 製作技巧庫（將發布到官網分享）

這裡放的是**給維護者與它的 agent 用的可執行知識**（skill＝一份 `SKILL.md`，frontmatter 加內文），
不是檔案、不是 log。判準只有一條：**照著做完，東西真的能跑**。

## 一、分層：核心與覆蓋

    skills/
      README.md                     ← 本檔：慣例與規則
      adb-author/                   ← 通用核心：原料 md → .adb（打包＋驗收＋交付紀律）
      adb-inspect/                  ← 通用核心：讀任何 .adb（走 adb MCP API，禁位元組 grep）
      ybh-adb-package/              ← 專案覆蓋：只寫《瑜伽師地論》與其他文字不同之處
      <text>-adb-package/           ← 日後其他法師各自新增

**規則是「重複的地方只能有一份」**：通用流程（驗收六類、交付前後 sha、硬鏈部署、行號是行表不是
`\n`、提取規則只能一份實作……）一律寫在 `adb-author`；專案覆蓋**只允許**寫：原料在哪裡、跨庫目標是誰、
著作清單與代號、專案特有的閘門與缺口、以及本專案工具的路徑。
理由不是整潔癖：我們真發生過同一批資料被兩支指令碼各寫一份規則，同一條記錄得到不同判定。
skill 也一樣——兩處寫同一件事，將來就會有一處是錯的。

## 二、一個 skill 必須具備

1. **frontmatter**：`name`（kebab-case、與目錄同名）、`description`（第三人稱，寫清楚**做什麼**與
   **什麼時候用**，這是被找到與被選中的唯一依據）、`version`（semver）。
2. **步驟可直接執行**：命令要能複製貼上；引數、環境變數、預設值都要寫出來，不能假設讀者知道我們的磁碟佈局。
3. **前提與依賴要誠實**：需要哪些外部原始碼或檔案、缺了會怎樣、替代方案及其代價。
   （範例：本地打包需要 adb-converter 的 TypeScript 原始碼，因為驗收用的就是閱讀器那支 `renderEmbed`／
   `parseTableBlock`；不寫這段，讀者會跑一半遇到 `Cannot find module` 而不知道是環境問題還是我們做錯。）
4. **邊界**：什麼可以自己做、什麼必須停下交人。寫成可判定的兩類，不要寫「小心處理」。
5. **已知缺口**：區分「待修」與「本質上做不到」，並說明**不要把它當工數**（例：源頭科判未編完的死錨、
   上級節點沒有正文首行）。這條能擋掉大量白費的工。
6. **驗證手段**：每個宣稱要附「怎麼量的」。沒實據的要寫「未驗證」，不圓話。

## 三、禁止進入 skill 與打包檔的東西

- **任何憑證**：路徑可以寫（`.local/smtp.json` 之類），值一律不得出現、不得印出、不得複製進信或 log。
- **客戶個資**：電子信箱、通訊軟體帳號、IP、瀏覽器 UA、來信全文。官網分享等於公開出版，
  這些一旦進檔就進歷史。
- 大體積成品（`.adb`、`.zip`、備份）——skill 只放方法與指令，不放產物。
- 絕對路徑作為**唯一**可行值：要寫成「可用環境變數覆寫，預設值＝我們的佈局」。

## 四、版本與打包

- **semver**：破壞性變更（步驟改了、引數名稱改了）進 major；新增能力進 minor；文字修訂進 patch。
- 每次打包都要產生**確定性**輸出與可比對的雜湊：同一份來源重複打包，zip 內條目順序與時間戳要一致
  （否則官網的 sha256 每次都在變，維護者無從判斷到底改沒改）。
- 上架清單沿官網既有模式（同 `www/adb/manifest.json`／`www/releases.json` 的形狀）：

      { name, version, description, file, sha256, size, buildTime, requires, notes[] }

- 交付前必跑的檢查——`bun run link-audit/tools/package-skills.ts` 會**自動**跑前五道，跑不過就不出包：
  1. 解壓後 `SKILL.md` 在 `<name>/SKILL.md` 且 frontmatter 可解析、`name` 欄與目錄一致，`version` 為 semver；
  2. `description` 非空且夠長（它是別人搜尋時唯一能看見的一行）；
  3. 掃一遍無憑證／個資樣式（email、IP、`password`／`token`、個人家目錄絕對路徑）；
  4. zip 條目路徑不含絕對路徑或 `..`（防路徑穿越），且**解壓回讀與來源逐字相同**；
  5. 字形：我方敘述一律繁體（`tools/check-glyphs.py`，同時掃清單 `manifest.json` 裡我們自己寫的字串）。
     偵測器跑不起來報「未跑成」並計入失敗，**不會**當成通過。
- 還有一道**只能人工**：照著 skill 從頭執行一次（至少在乾淨環境跑「步驟 0 體檢」）。
  這道沒辦法自動化，所以不寫進打包器的綠字裡冒充——跑不通的 skill 不釋出。
- 打包全綠之後、把人交出去之前，再跑一次 `python link-audit/tools/verify-skill-provenance.py`：
  它比的是**版控＝磁碟＝成品**三點相同。為什麼要三點：只比「成品 vs 版控」會漏掉
  「改了原始檔卻忘了提交」——那時成品還是舊的、和版控一模一樣，檢查照樣報綠，
  下一個人重跑打包就會得到一顆「全綠但倉庫裡找不到對應原始檔」的成品。

## 五、字形規則（現在就要定，等有幾十只 skill 上架再補就來不及）

1. **我方敘述一律繁體**；交付前逐檔掃「僅簡體所有」的字形（与、为、们、这、发、处、错、让、复……）。 <!-- glyph:raw 本行是在列舉簡體字形作為反例，不是敘述用字 -->
   注意偽陽性：列、布、化、据（據）、显 之類要另行判斷，否則檢查會變成噪音工廠。 <!-- glyph:raw 同上：這幾個字是要拿來舉例的 -->
   這條不靠人記憶：跑 `python link-audit/tools/check-glyphs.py`，它已接進打包檢查（⑤）。
2. **引用初級資料與來函原文保留原始字形，不做繁簡轉換。**
   資料維護者寫的是簡體，正典裡引他原話就該是簡體；轉換等於替他改話——
   這比「字形不一致」嚴重得多，而且是記錄誠信問題，不是排版問題。
3. 因此**禁止對正典做無差別全檔轉換**：一次全檔 diff 會同時覆蓋我方敘述與引用原文，
   兩者分不開，事後就分辨不出哪幾處是我們替來源改了字。
   做法：按節或按段處理，並保留引用行，事後驗證「引用行仍是原字形」要寫進檢查。

## 六、待使用者決定的兩件事

1. **skill 的正本放哪裡**：現行放在 ybh 工作區（本目錄）。既然要跨文字共用與官網分享，
   正典位置建議移到中性且與釋出工具同處的地方（例如母區 `skills/`，它已有 `mcp/` 之類共用資產），
   各文字倉只留自己的覆蓋目錄並引用核心。這一搬動會影響別人，所以沒有擅自動手。
2. **授權與具名**： adb 官網目前對資料庫用 CC0／Apache-2.0 的標注方式；skill 要採哪一種、
   以及「誰寫的」如何呈現（維護者具名？「由 accelon26 維護團隊」？），需使用者定。
   這會寫進 skill 的 frontmatter 或清單頁，事後改比事前定麻煩。
